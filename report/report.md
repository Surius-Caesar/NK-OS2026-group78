## 实验整体逻辑分析

### 本章节的逻辑主线

对于动辄上百万行的Linux/Windows等操作系统，几千行的ucore是一只“麻雀”。而本实验是要做出“麻雀的骨架”，即一个能格式化输出，然后陷入死循环的最小可执行内核。

本章节整体逻辑线是“**硬件启动 → 地址与布局固化 → 运行环境搭建 → 功能自底向上实现 → 构建与验证**”，按照如下顺序展开：
1. **明确系统启动基础依赖**：操作系统内核不具备自举能力，无法自行加载到内存运行，必须由前置引导程序完成硬件初始化与内核加载工作。在 QEMU 模拟的 RISC-V 平台中，由 OpenSBI 固件承担 Bootloader 的角色，作为内核启动的前置运行环境。
2. **确定内核合法内存入口地址**：内核运行入口由硬件与固件规范决定，不可随意自定义。QEMU 上电复位地址为 `0x1000`，系统会自动加载 OpenSBI 固件至 `0x80000000`；同时固件约定将内核镜像固定加载至 `0x80200000`，初始化完成后跳转至该地址移交执行权。
3. **通过链接脚本固化内核内存布局与程序入口**：为严格匹配固件加载规则，通过 `tools/kernel.ld` 链接脚本将内核运行基地址配置为 `BASE_ADDRESS = 0x80200000`，统一规划各代码段、数据段的内存映射关系，并通过 `ENTRY(kern_entry)` 指定全局内核入口，保证编译出的镜像符合裸机运行要求。
4. **搭建 C 语言运行基础环境**：内核最先执行的是汇编入口代码，而 C 语言函数的执行依赖栈空间。因此在汇编启动阶段需要手动初始化内核栈，为后续 C 代码调用、函数栈帧分配提供运行支撑，实现从汇编控制流到 C 语言控制流的平稳切换。
5. **完成内核初始化并实现启动反馈输出**：进入 C 语言入口函数 `kern_init` 后，手动清零 `.bss` 未初始化数据段，完成内核基础运行环境初始化；随后调用打印接口输出内核启动日志，最终通过死循环常驻运行，保证最小内核正常工作。
6. **自底向上自主实现格式化打印功能**：裸机内核没有 glibc 标准库支持，无法直接调用系统打印函数。本实验基于 OpenSBI 提供的 SBI 系统服务，通过内联汇编实现 `ecall` 特权级调用，从底层单字符输出接口逐层封装，最终自主实现通用的格式化打印函数 `cprintf`，搭建起内核的基础调试输出能力。
7. **配置自动化构建流程并完成内核运行**：通过编写 Makefile 构建脚本，自动化完成源码编译、目标文件链接、ELF 内核生成、objcopy 镜像格式转换的全流程，最终输出 QEMU 可直接加载运行的 BIN 格式内核镜像，实现最小内核的一键构建与启动。
8. **基于 GDB 调试完成流程验证**：借助 QEMU + GDB 远程调试机制，对内核启动全流程进行跟踪验证。通过设置断点、单步执行、查看寄存器与内存数据，完整观测从机器上电复位、OpenSBI 固件运行、内核加载跳转至内核代码执行的全过程，确保整体启动流程正确可靠。
### 功能的逐步实现

上述逻辑主线落实到代码层面，各功能按以下顺序逐步实现：
1. **定义内核内存布局与入口规则**
编写链接脚本，指定内核加载基地址与入口符号，划分各程序段。这一步完成后，能编译出地址符合 OpenSBI 要求的可链接目标文件，解决裸机程序地址不匹配的问题。
2. **编写汇编入口，搭建 C 运行环境**
实现`entry.S`，定义内核栈并设置栈指针，完成汇编到 C 代码的跳转。内核获得栈环境，具备执行 C 语言代码的基础条件。
3. **实现内核基础初始化逻辑**
编写`kern_init`，增加 BSS 段清零代码。内核全局变量可以正常初始化，C 代码能够安全使用全局数据。
4. **封装底层 SBI 调用接口**
利用内联汇编实现 SBI 通用调用函数，完成 ecall 特权级切换。内核获得调用 OpenSBI 底层服务的能力。
5. **实现控制台底层字符输出**
基于 SBI 调用封装单字符输出函数，内核拥有向控制台输出单个字符的基础 IO 能力。
6. **实现格式化打印 cprintf**
在单字符输出之上，实现字符串输出与格式化解析，完成`cprintf`。内核可以打印带变量的格式化信息，用于调试输出。
7. **编写构建脚本，自动化生成镜像**
配置 Makefile，串联编译、链接、objcopy 镜像转换流程。一键生成 QEMU 可加载的 bin 镜像，能够启动运行最小内核。
8. **增加调试支撑，验证全部功能**
配置 QEMU+GDB 远程调试环境，支持断点、单步、寄存器查看。能够跟踪内核执行，定位启动、内存、链接相关 bug，验证所有功能正确性。

## 实验内容与实现

### 功能模块：

#### 1. **启动与入口**
`kern_entry`（`kern/init/entry.S`）：存放内核第一条执行指令，仅完成两项工作。`la sp, bootstacktop` 初始化内核栈；由于栈向低地址方向增长，栈指针设置在栈预留空间的末端。`tail kern_init` 通过尾调用跳转至C代码入口，不保存返回地址。

`kernel.ld`（`tools/kernel.ld`）：链接脚本。`ENTRY(kern_entry)` 指定内核入口符号；`BASE_ADDRESS = 0x80200000` 设置内核加载地址，并将`.text.kern_entry`放置在最前端，保证入口代码落在目标地址；使用`PROVIDE(etext/edata/end)`导出各段边界符号，供C代码引用。

#### 2. **内核初始化**
`kern_init`（`kern/init/init.c`）：C语言层面的内核入口函数。借助`edata`与`end`符号，调用`memset`清零`.bss`段。ELF文件中`.bss`仅记录起止位置，不存储实际数据，需要在内核运行时手动清零；裸机环境无标准库，`memset`需要自行实现。完成初始化后调用`cprintf`打印启动提示，最后执行`while(1);`死循环保持内核驻留。

#### 3. **输出链（自底向上）**
`sbi_call`（`libs/sbi.c`）：利用内联汇编执行`ecall`指令，完成S特权级到M特权级的跨特权级调用。遵循SBI调用约定：功能号存入`a7`，参数放入`a0~a2`，返回值从`a0`获取。这类寄存器直接操作无法单纯用C语言实现，必须依靠内联汇编。

`sbi_console_putchar`（`libs/sbi.c`）：基于`sbi_call`封装，使用功能号`SBI_CONSOLE_PUTCHAR(1)`，将输出单个字符的底层能力封装为普通C函数。

`cons_putc`（`kern/driver/console.c`）：驱动层简易封装，隔离底层设备相关调用，实现设备层与上层IO解耦。

`cputch / cputchar / cputs`（`kern/libs/stdio.c`）：`cputch`输出单个字符并统计输出长度；`cputs`循环调用底层接口逐字符输出字符串，并自动追加换行。

`printfmt.c` 与 `cprintf`（`libs/printfmt.c`、`kern/libs/stdio.c`）：`printfmt.c`负责解析格式化字符串、转换可变参数；`cprintf`将格式化后的文本交由`cputch`输出，功能接近标准库`printf`。

`defs.h / riscv.h`（`libs/`）：`defs.h`提供基础数据类型、`ROUNDDOWN`等宏，替代C标准库；`riscv.h`将`csrr`、`csrw`等CSR指令封装为`read_csr`、`write_csr`宏。

#### 4. **构建与调试**
`Makefile` 与 `function.mk`：串联完整工程流程：源码编译、链接生成ELF文件、`objcopy`转为BIN镜像、启动QEMU。`make qemu`通过`-device loader`参数将内核镜像加载至`0x80200000`；`make debug`启动处于暂停状态的QEMU，`make gdb`启动GDB并建立远程调试连接。

### 练习1：理解内核启动中的程序入口操作

**负责人：** 2413993-徐锐

`la sp, bootstacktop`将 `bootstacktop` 的地址装入栈指针寄存器 `sp`；因为 RISC-V 的栈从高地址向低地址增长，所以要把 `sp` 初始化为 `bootstacktop`，而不是 `bootstack`。总之；目的是为了完成内核栈初始化。

`tail kern_init`目的是直接跳转到 `kern_init`，不保存新的返回地址，不期望返回到 `kern_entry`。目的是将控制权永久性交给C语言内核入口，符合内核初始化的逻辑。

## 3. 调试过程与观察结果

### 3.1 查看复位地址 PC

在 GDB 中输入：

```gdb
i r pc
```

输出：

```text
pc             0x1000   0x1000
```


RISC-V 硬件加电后，PC 停在 `0x1000`。该地址是 QEMU 内置启动固件的入口。

---

### 3.2 查看 `0x1000` 处的最初指令

在 GDB 中输入：

```gdb
x/10i $pc
```

输出：

```asm
=> 0x1000:      auipc   t0,0x0
   0x1004:      addi    a1,t0,32
   0x1008:      csrr    a0,mhartid
   0x100c:      ld      t0,24(t0)
   0x1010:      jr      t0
   0x1014:      unimp
   0x1016:      unimp
   0x1018:      unimp
   0x101a:      0x8000
   0x101c:      unimp
```

加电后最初执行的几条指令位于 `0x1000` 开始的位置。  

---


### 3.3 单步执行 `0x1000` 处最初指令并观察寄存器

在 GDB 中连续执行以下命令：

```gdb
si
i r t0
si
i r a1
si
i r a0
si
x/gx 0x1018
i r t0
si
i r pc
```
对应输出汇总如下：

```text
(gdb) si
0x0000000000001004 in ?? ()
(gdb) i r t0
t0             0x1000   4096
(gdb) si
0x0000000000001008 in ?? ()
(gdb) i r a1
a1             0x1020   4128
(gdb) si
0x000000000000100c in ?? ()
(gdb) i r a0
a0             0x0      0
(gdb) si
0x0000000000001010 in ?? ()
(gdb) x/gx 0x1018
0x1018: 0x0000000080000000
(gdb) i r t0
t0             0x80000000       2147483648
(gdb) si
0x0000000080000000 in ?? ()
(gdb) i r pc
pc             0x80000000       0x80000000
```

`si` 执行完当前指令后，PC 会停在下一条指令。因此，每次 `i r` 看到的是上一条指令执行后的结果。



1. 执行 `auipc t0,0x0` 后，PC 从 `0x1000` 变为 `0x1004`，`t0` 变为 `0x1000`。  
   说明该指令把当前 PC 加上 `0x0 << 12`，结果写入 `t0`。

2. 执行 `addi a1,t0,32` 后，PC 从 `0x1004` 变为 `0x1008`，`a1` 变为 `0x1020`。  
   因为此时 `t0 = 0x1000`，所以 `a1 = 0x1000 + 32 = 0x1020`。  
   在 RISC-V 启动协议中，`a1` 通常用于传递设备树 DTB 地址。

3. 执行 `csrr a0,mhartid` 后，PC 从 `0x1008` 变为 `0x100c`，`a0` 变为 `0x0`。  
   说明当前 hart ID 为 0，即主核。  
   在 RISC-V 启动协议中，`a0` 通常传递 hart ID。

4. 执行 `ld t0,24(t0)` 后，PC 从 `0x100c` 变为 `0x1010`，`t0` 变为 `0x80000000`。  
   此时旧的 `t0 = 0x1000`，所以访问地址为 `0x1000 + 24 = 0x1018`。  
   用 `x/gx 0x1018` 查看该地址，得到 `0x0000000080000000`。  
   因此这条指令从 `0x1018` 读出了下一阶段入口地址 `0x80000000`，即 OpenSBI 入口。

5. 执行 `jr t0` 后，PC 从 `0x1010` 变为 `0x80000000`。  
   说明程序跳转到 `t0` 保存的地址，控制权从 QEMU 启动固件交给 OpenSBI。

因此，加电后最初执行的几条指令位于 `0x1000` 开始的位置。  
它们的主要功能是：准备启动参数，读取 hart ID 和 DTB 地址，从 `0x1018` 加载 OpenSBI 入口 `0x80000000`，最后跳转到 OpenSBI。

### 3.4 进入 OpenSBI

执行 `jr t0` 后，PC 变为 `0x80000000`，进入 OpenSBI。  
在 GDB 中查看该地址开始的指令：

```gdb
x/10i $pc
```

输出：

```asm
=> 0x80000000:  csrr    a6,mhartid
   0x80000004:  bgtz    a6,0x80000108
   0x80000008:  auipc   t0,0x0
   0x8000000c:  addi    t0,t0,1032
   0x80000010:  auipc   t1,0x0
   0x80000014:  addi    t1,t1,-16
   0x80000018:  sd      t1,0(t0)
   0x8000001c:  auipc   t0,0x0
   0x80000020:  addi    t0,t0,1020
   0x80000024:  ld      t0,0(t0)
```


`0x80000000` 处是 OpenSBI 的启动代码。  
我们直接在内核入口 `kern_entry` 处下断点，让程序运行到内核开始执行的位置。

---

### 3.5 断点验证内核入口

在内核入口符号处设置断点：

```gdb
b* kern_entry
```

输出：

```text
Breakpoint 1 at 0x80200000: file kern/init/entry.S, line 7.
```

 
`b* kern_entry` 等价于 `break *kern_entry`，表示在符号 `kern_entry` 对应的地址处设置执行断点。  
GDB 根据调试符号将其解析为地址 `0x80200000`，对应源文件 `kern/init/entry.S` 第 7 行。  
这说明链接脚本指定的内核入口正是 `0x80200000`，调试符号也已正确加载。

然后继续运行：

```gdb
c
```

输出：

```text
Continuing.

Breakpoint 1, kern_entry () at kern/init/entry.S:7
7           la sp, bootstacktop
```

 
`c` 表示继续执行。OpenSBI 完成初始化后，最终跳转到 `0x80200000`，命中刚才设置的 1 号断点。  
GDB 显示当前停在 `kern_entry` 函数，源文件 `kern/init/entry.S` 第 7 行，即将执行的源码是 `la sp, bootstacktop`。  
这说明控制权已经从 OpenSBI 移交给内核，内核开始执行第一条指令。

随后查看当前 PC：

```gdb
i r pc
```

输出：

```text
pc             0x80200000       0x80200000 <kern_entry>
```

PC 当前为 `0x80200000`，对应符号 `kern_entry`，确认内核入口地址正确。

查看内核入口处的指令：

```gdb
x/5i $pc
```

输出：

```asm
=> 0x80200000 <kern_entry>:     auipc   sp,0x3
   0x80200004 <kern_entry+4>:   mv      sp,sp
   0x80200008 <kern_entry+8>:   j       0x8020000a <kern_init>
   0x8020000a <kern_init>:      auipc   a0,0x3
   0x8020000e <kern_init+4>:    addi    a0,a0,-2
```

内核入口第一条指令是 `auipc sp,0x3`，用于计算内核栈顶地址并设置栈指针 `sp`。  
第二条 `mv sp,sp` 实际是 `addi sp,sp,0`，因为 `bootstacktop` 的低 12 位为 0，所以看起来像空操作。  
第三条 `j 0x8020000a <kern_init>` 直接跳转到 C 函数 `kern_init`，开始内核初始化。

最后查看当前 PC 对应的符号：

```gdb
info symbol $pc
```

输出：

```text
kern_entry in section .text
```

当前 PC 对应符号 `kern_entry`，位于 `.text` 段，确认已经停在内核代码入口处。  


OpenSBI 完成初始化后，最终跳转到 `0x80200000`，即内核入口 `kern_entry`。  
内核第一条指令 `auipc sp,0x3` 用于设置内核栈指针，随后跳转到 `kern_init` 执行 C 代码。

## 4. 问题回答

### 问题：RISC-V 硬件加电后最初执行的几条指令位于什么地址？它们主要完成了哪些功能？

**答案：**

在 QEMU 模拟的 RISC-V `virt` 机器上，RISC-V 硬件加电后，CPU 最初从：

```text
0x1000
```

开始执行指令。

最初几条指令为：

```asm
0x1000: auipc t0,0x0
0x1004: addi  a1,t0,32
0x1008: csrr  a0,mhartid
0x100c: ld    t0,24(t0)
0x1010: jr    t0
```

它们的主要功能如下：

| 指令 | 功能 |
|---|---|
| `auipc t0,0x0` | 获取当前 PC 附近地址，`t0 = 0x1000` |
| `addi a1,t0,32` | 设置 `a1 = 0x1020`，通常指向设备树 DTB |
| `csrr a0,mhartid` | 读取当前 hart ID，主核为 `a0 = 0` |
| `ld t0,24(t0)` | 从地址 `0x1018` 读取下一阶段入口 `0x80000000` 到 `t0` |
| `jr t0` | 跳转到 `0x80000000`，进入 OpenSBI |

因此，加电后最初执行的指令位于 `0x1000`，这些指令完成启动参数准备，并跳转到 OpenSBI。OpenSBI 再进行主初始化，最终跳转到内核入口 `0x80200000`。

## 5. 结论

通过 GDB 跟踪 QEMU 模拟的 RISC-V 启动过程，可以清晰看到启动链：

```text
0x1000  QEMU 启动固件
   ↓
0x80000000  OpenSBI
   ↓
0x80200000  内核 kern_entry
```

硬件加电后最初执行的指令位于 `0x1000`，主要完成：

1. 获取当前 PC；
2. 设置 DTB 地址到 `a1`；
3. 读取 hart ID 到 `a0`；
4. 从 `0x1018` 加载 OpenSBI 入口 `0x80000000`；
5. 跳转到 OpenSBI。

OpenSBI 完成初始化后，将控制权交给内核入口 `0x80200000`，内核开始执行 `kern_entry` 的第一条指令 `auipc sp,0x3`，设置内核栈。

## 实验总结与收获

### 对操作系统的理解

本实验中重要的知识点与对应 OS 原理中的知识点，二者的含义、关系和差异如下表所示：
| OS 原理知识点 | 含义 | 与 Lab1 的对应关系 | 差异 |
|---|---|---|---|
| 引导与启动 | OS 原理阐述"加电 → 固件 → 引导 → OS"的通用启动链，说明 OS 无法自举、需逐级引导加载 | Lab1 用 RISC-V + OpenSBI 具体实现了这条链：QEMU 固件 → OpenSBI → 内核 | 原理覆盖多级链（BIOS/UEFI → GRUB → OS，含安全启动）；Lab1 仅有 OpenSBI 单级引导，无安全检查 |
| 特权级与双模保护 | OS 原理强调用户态 / 内核态隔离以保护系统资源 | Lab1 展示了 M/S/U 三级特权模式，并说明了固件为何必须运行在最高特权级 | 原理通常只讲"用户态 vs 内核态"两态；Lab1 多出固件所在的 M 态，且保护隔离在本实验中尚未真正实施 |
| 系统调用与陷入机制 | OS 原理中系统调用是用户程序请求内核服务的受控入口（功能号 + 寄存器传参 + 陷入 + 返回） | Lab1 中内核通过 `ecall` 陷入 M 态请求 OpenSBI 服务，机制完全同构 | 原理场景是"用户程序 → 内核"；Lab1 是"内核 → 固件"，真正的用户态系统调用在后续实验（如 Lab5）才会出现 |
| 程序地址空间 / 内存布局 | OS 原理中进程地址空间包含 text/data/bss/heap/stack 等区域 | Lab1 通过链接脚本规定了内核镜像在物理内存中的静态布局 | 原理中的地址空间是"虚拟地址 / 进程级"概念；Lab1 仅是内核镜像的物理内存静态布局，尚未引入虚拟内存 |
| 内核初始化 / 运行环境 | OS 原理中 OS 启动后需要初始化各类运行环境（中断、调度、内存等） | Lab1 的 `kern_init` 完成清 BSS、设栈等最基础的初始化工作 | 原理的初始化范围大得多；Lab1 只完成最基础的输出与清零 |
| 地址相关代码 | OS 原理中代码与虚拟内存、动态链接、位置无关代码（PIC/PIE）相关 | Lab1 说明了内核因"地址相关"必须被加载到固定地址 `0x80200000` | Lab1 仅停留在"为何需要固定地址"；未实现 PIC/PIE 重定位等机制 |
| 编译、链接与加载 | OS 原理 / 前置知识介绍程序从源码到可执行文件的构建过程 | Lab1 用交叉编译 + 链接脚本 + ELF → BIN 实际操作了裸机构建流程 | 原理一般不强调"无标准库"的裸机构建；Lab1 突出了自举依赖 |

**OS 原理中很重要（目前为止学到的）、但在本实验中没有对应上的知识点：**

1. **进程与线程管理**：Lab1 中不存在"进程"概念，整个内核只是一个死循环单程序，进程的创建、状态转换与上下文切换均未涉及。
2. **CPU 调度算法**：由于没有多任务，自然不存在调度器与各种调度算法（如先来先服务、时间片轮转等）。
3. **虚拟内存与地址转换**：Lab1 内核直接运行在物理地址空间，未开启分页，也没有 MMU 地址转换、页表管理等内容。
4. **物理内存分配与回收**：内核尚无动态内存管理机制，未涉及伙伴系统、slab 等分配算法。
